# 1. 标题

格式：

```
[模块][功能] 简短描述
```

例如：

```
[CMIS][CDB] Firmware Download过程中CdbStatus始终Busy

[I2C Slave] STM32H563在STOPF后无法继续响应Host读请求

[MSM] ModuleReady状态下执行ResetS导致状态机卡死

[DSP API] 温度读取接口返回异常值65535
```

要求：

```
看标题就知道：
1. 哪个模块
2. 什么问题
3. 大概现象
```

# 问题背景

不要直接写现象。

先写：

```
这个问题是在什么场景出现的
```

例如：

```
# 问题背景

项目：
800G DR8

软件版本：
FW v1.2.3

测试环境：
Arista 7060X6

测试项：
Firmware Download

触发条件：

1. Host执行Firmware Download
2. Download完成
3. Host执行Run Image

期望：

Module切换到新Firmware并进入Ready状态
```

# 问题现象

这一部分只写事实。

不要写猜测。

例如：

```
# 问题现象

现象：

Host执行Run Image后：

- Module未重启
- CdbStatus保持Busy
- CdbCommandCompleteFlag未置位

日志：

15:23:01 Run Image Command
15:23:02 CdbStatus=Busy
15:23:05 CdbStatus=Busy
15:23:10 CdbStatus=Busy
```

错误示例：

```
应该是状态机有问题
```

这种属于分析，不属于现象。

# 影响范围

这是很多新人最容易漏掉的。

例如：

```
# 影响范围

影响功能：

- Firmware Upgrade

不影响：

- CMIS基本访问
- LOS检测
- 温度监控

影响概率：

100%

影响版本：

v1.2.3
```

# 复现步骤

这是最重要的一部分。

必须做到：

```
别人拿到模块
照着步骤
100%复现
```

例如：

```
# 复现步骤

1. 上电
2. 等待ModuleReady
3. Firmware Download Image A
4. Execute Run Image
5. Poll CdbStatus

结果：

CdbStatus一直Busy
```

# 分析过程

这一部分不要省略。

很多人只写：

```
原因找到了
```

半年后自己都看不懂。

应该记录：

```
# 分析过程

分析1：

确认Host Command正确

结果：

Command Header正常

--------------------------------

分析2：

确认CDB Trigger

结果：

Command被成功接收

--------------------------------

分析3：

查看CDB Worker

发现：

状态停留在

CDB_STATE_EXECUTING

--------------------------------

分析4：

检查状态转移条件

发现：

flash_verify_result未更新
```

这样以后别人能看到：

```
你排除了什么
你验证了什么
```

这部分价值最大。

# 根因（Root Cause）

一定要单独写。

格式：

```
# 根因

直接原因：

flash_verify_result变量未更新

代码位置：

firmware_upgrade.c

原因：

Verify任务执行完成后
未发送EVENT_VERIFY_DONE

导致：

CDB状态机无法从EXECUTING进入COMPLETED
```

# 修复方案

例如：

```
# 修复方案

修改：

firmware_upgrade.c

增加：

EVENT_VERIFY_DONE

修改前：

VERIFY_DONE
    -> no action

修改后：

VERIFY_DONE
    -> set flash_verify_result
    -> post EVENT_VERIFY_DONE
```

# 验证结果

证明问题真的解决了。

例如：

```
# 验证结果

验证版本：

v1.2.4

执行次数：

50次

结果：

PASS

异常：

0次

平均升级时间：

23.4s
```

# 经验总结

很多人不写这一部分。

实际上这部分最有价值。

例如：

```
# 经验总结

问题本质：

状态机事件丢失

暴露的问题：

1. 状态机无超时机制
2. Event Queue无统计
3. 无状态迁移日志

改进措施：

1. 增加状态机超时保护
2. 增加Event Trace
3. 增加状态迁移日志
```

这部分其实已经从：

```
解决一个Bug
```

升级成：

```
提升整个系统架构
```
